# ORG.md v0.5 Reference Implementation Design

**Status:** Approved in design review

**Date:** 2026-08-21

**Target:** `orgmd` 0.5.0 in the `orgmd/spec` repository

## Context

The repository publishes the ORG.md specification, project governance bundle,
and documentation site, but it does not yet contain the v0.5 reference
implementation described by `ROADMAP.md` and `AGENT-BRIEF.md`. The local
workspace was an older export, so design work first synchronized it to the
authoritative public repository at commit
`ec8adcd08b183881a4666a09ade918afd177778b`.

This is an architectural addition: a deterministic parser, validator,
resolver, compiler, health checker, initializer, importer, schema,
conformance corpus, CI integration, and release documentation. The work will
remain in this repository so the specification, conformance cases, dogfood
bundle, and implementation change together under one review process.

`SPEC.md` is the normative contract. `AGENT-BRIEF.md` supplies build order and
repository conventions but does not override the specification. In
particular, the brief's older `contested` and `superseded` revision statuses
are replaced by the v0.3.1 ratification vocabulary `draft`, `approved`, and
`rejected`; contestation and retirement are represented only through the
identity entry's `lifecycle` mapping. The fifth CLI command is `adopt`, as
specified by the v0.5 roadmap.

## Goals

The release will:

1. Provide one auditable TypeScript package named `orgmd` for Node.js 20 and
   later.
2. Implement Core-conformant parsing, validation, content identifiers,
   context identifiers, and Mode A resolution.
3. Expose the resolver as a library API and five deterministic CLI commands:
   `validate`, `compile`, `doctor`, `init`, and `adopt`.
4. Produce only the two v0.5 advisory projections: an AGENTS.md fragment and
   a plain prompt block.
5. Publish the entry front-matter JSON Schema and the first deterministic
   Core conformance vectors.
6. Validate and diagnose this repository's `org/` bundle in CI.
7. Make the npm artifact and GitHub Pages documentation ready for a 0.5.0
   release without storing release credentials or publishing automatically.

## Non-goals

This release will not implement an MCP gate, enforcement, authentication,
signing, `org.lock`, adapters, retrieval, workflow, audit storage, a handbook
renderer, Desk UI, hosted services, a plugin system, benchmark scoring, or
v0.6+ functionality. `adopt` is a local deterministic importer, not an
adapter and not a model-backed classifier.

The roadmap also calls for real BoundFor and FieldReport dogfood bundles.
Those organisations' source content is not present in this repository and
will not be fabricated by the implementation. The CLI, schema, and
conformance work will make those adoptions possible; landing the real bundles
remains a separately reviewed content task owned by those organisations.

## Repository and package layout

The root becomes a private npm workspace. It owns the lockfile and common
commands for formatting checks, type checking, tests, builds, package
verification, and dogfood validation. The publishable package lives at
`packages/orgmd/` and contains the `orgmd` executable and public library
exports.

```text
package.json
package-lock.json
tsconfig.json
packages/orgmd/
  package.json
  src/
    cli/
    compiler/
    diagnostics/
    doctor/
    identifiers/
    importer/
    init/
    model/
    parser/
    resolver/
    validation/
  test/
schema/entry.schema.json
conformance/core-v0.1/
docs/cli.md
```

Production dependencies will be limited to a YAML parser, JSON Schema
validator, RFC 8785 canonicalizer, and a light argument parser if Node's
built-ins would make the interface less clear. Filesystem access, hashing,
line handling, interactive input, and atomic writes use Node built-ins.
TypeScript, Vitest, Node types, and repository-only formatting/static-analysis
tools are development dependencies.

## Component boundaries

Each component has one public responsibility and returns values plus typed
diagnostics rather than printing or exiting directly.

- **Parser:** converts Markdown bytes into ordered entry containers, source
  ranges, YAML front matter, and bodies. It implements the v0.3.1 grammar,
  including UTF-8 BOM handling, CRLF normalization, exact delimiters, blank
  line requirements, fenced-code awareness, and duplicate YAML-key rejection.
- **Model and bundle loader:** assigns domains from the bundle structure,
  loads identity metadata, preserves revision sets, and rejects duplicate or
  malformed identities without applying resolution rules.
- **Validation:** applies `schema/entry.schema.json` and semantic rules the
  schema cannot express safely, including domain-specific fields, effective
  revisions, lifecycle references, scope lattices, synchronized provenance,
  policy actions/effects/routes, revisit requirements, and last-resort
  ownership.
- **Identifiers:** constructs the normative bundle metadata and entry
  canonical forms, serializes them with RFC 8785 JSON Canonicalization Scheme,
  and computes SHA-256 content and context identifiers exactly as `SPEC.md`
  section 7 defines.
- **Resolver:** consumes an ordered root-to-leaf bundle path, clearance, Core
  Mode A, and a validated model. It returns an immutable resolved context,
  withheld markers, reliance metadata, versions, identifiers, and sorted
  diagnostics.
- **Compiler:** transforms only a successful resolved context into an
  advisory AGENTS.md fragment or prompt block. It never reads raw bundles.
- **Doctor:** computes actionable health findings from validated bundles. Its
  date source is injected so tests remain deterministic.
- **Initializer and importer:** create proposed bundle content through the
  same model and validation APIs used for reads. They write only after a
  successful preview and validation pass.
- **CLI:** maps arguments, output formats, and exit codes onto the components.
  No domain rule lives only in command handlers.

## Data flow and resolution

The common pipeline is:

```text
read bytes -> parse -> validate -> identify bundle -> resolve context
           -> compile projection or produce diagnostics
```

Validation never mutates source files. The resolver runs only on validated
models and implements Core Mode A. It selects the highest approved revision,
applies retirement and reliance-scoped contestation, evaluates the root scope
lattice, and resolves the ordered path. Ordinary definitions use
closest-wins. Ownership and decisions remain anchored rootward unless a valid
delegation permits a descendant definition. Constraints stack; a closer
same-ID constraint must structurally narrow both the action set and effect.
Clearance changes emission after applicability and resolution, never before
them.

Any invalid bundle at a node fails that node with the blast radius required by
the specification. There is no silent fallback to an ancestor. Filesystem
enumeration and YAML mapping order cannot affect the result. Diagnostics and
resolved records are sorted by stable semantic keys before rendering.

The public resolver API accepts an explicit ordered bundle path and clearance
set. CLI compilation accepts a target directory and discovers bundle
ancestors containing `org.md`, ordered from the outermost ancestor to the
target. It reports that path and the resolved bundle versions. Library callers
that already know the topology bypass discovery by supplying the path
directly.

## Diagnostics and failure behaviour

Every diagnostic contains a stable code, severity, message, source path,
optional line/column, optional entry ID, and machine-readable details. Human
output is concise and actionable. `--json` emits one documented JSON shape
for CI and editor integrations. Sorting is deterministic by source path,
position, entry ID, and code.

All commands use these exit codes:

- `0`: successful operation with no blocking findings.
- `1`: invalid content, resolution failure, or blocking doctor findings.
- `2`: invalid invocation, filesystem failure, or unexpected internal error.

Commands that write use a temporary sibling followed by an atomic rename.
Validation or resolution errors prevent output replacement. Unexpected
failures show a stable high-level diagnostic; stack traces are available only
through an explicit debug option.

## CLI behaviour

### `orgmd validate [path]`

The default path is the current directory. The command discovers all Markdown
entries in the bundle, then checks grammar, schema, semantic rules, identity
metadata, and Core identifiers. It never changes files. `--json` selects
structured diagnostics.

### `orgmd compile [path] --target <agents-md|prompt>`

Compilation discovers the ordered bundle path, resolves it at the requested
clearance, and emits exactly one advisory projection. `--all` emits both
targets and is mutually exclusive with `--target`. Output includes the Core
spec version, source bundle versions, content IDs, and context ID. The
AGENTS.md target is bounded by generated `orgmd:begin` and `orgmd:end`
comments. The prompt target is plain text. Stale and contested entries are
marked as required; drafts, rejected revisions, retired entries, and
non-effective revisions are not emitted. `--output` writes atomically;
otherwise output goes to stdout.

### `orgmd doctor [path]`

Doctor reports overdue revisit dates, missing recommended revisit dates,
orphaned owners, synchronized sources and divergence states that can be
determined without an adapter, unresolved entries, and native-versus-synced
counts and percentages by domain. Missing `revisit` where the specification
only says SHOULD, synchronized-source presence, and ratio metrics are
advisory; they remain visible but do not make an otherwise healthy bundle
fail. Missing required `revisit`, overdue reviews, orphaning, divergence, and
resolution failures are blocking and exit with code 1 so CI can gate on them.
The underlying API receives an explicit date for repeatable tests.

### `orgmd init [path]`

Interactive mode asks for the organisation name, tone, contested terminology,
one non-negotiable policy, and owners. It writes a minimal three-file Core
bundle only after the proposed bundle validates and doctors clean.
Non-interactive flags supply the same required values for tests and
automation. Existing files are not overwritten unless an explicit overwrite
option names them, and preview remains available before writing.

### `orgmd adopt <source> [path]`

Adopt accepts AGENTS.md, CLAUDE.md, or ordinary Markdown. It deterministically
splits heading-based sections and list guidance into candidate definitions and
constraints, preserving source text and references. Every candidate is
`status: draft`; ownership, scope, revisit date, and any ambiguous domain are
shown for human confirmation. It uses no model and makes no approval claim.
The default is a rendered preview. `--write` is required to create files, and
the source is never modified or deleted.

## Schema and conformance corpus

`schema/entry.schema.json` describes the common front-matter contract and the
conditional synchronized-source fields. Domain rules that depend on the
containing file remain semantic validation rules and are covered by fixtures.
The schema declares the v0.3.1 status vocabulary, required `rev`, and the
constraint vocabulary without carrying forward the stale brief language.

`conformance/core-v0.1/` is data first, so other implementations can consume
it without running TypeScript. A manifest identifies the conformance version
and spec version. Each case contains input bundle trees and expected JSON for
diagnostics, resolved entries, withheld markers, content IDs, context IDs, or
compiler bytes as appropriate. Initial cases cover parser boundaries,
ratification and lifecycle, scope, path designation, authority anchoring and
delegation, structural policy narrowing, failure blast radius, clearance,
canonicalization, and both advisory projections.

Tests execute every vector through the public library. Additional permutation
tests vary directory enumeration and irrelevant input order, repeat runs, and
assert byte-identical results for the same tree, identity, mode, and
clearance.

## Dogfood migration

The current `org/decisions/DEC-0003.md` uses the removed `superseded` status.
The implementation PR will propose restoring its ratification state to
`approved` without changing its meaning and recording retirement under
`org.identity.lifecycle.dec.0003`. The reviewed lifecycle act will identify
`role.editor`, use the review/merge date, and reference DEC-0022. This content
change must be explicitly ratified in review by the current `role.editor`;
tooling will not invent attribution. Once ratified, `orgmd validate org` and
`orgmd doctor org` must both pass in CI.

## Testing and CI

Implementation follows test-driven development. Each parser, validation,
identifier, resolver, compiler, doctor, initializer, importer, and CLI
behaviour begins with a failing unit or integration test. Tests use temporary
directories and injected clocks; they do not depend on network access or the
caller's locale.

A new CI workflow runs on pull requests and pushes. It performs a clean npm
install, formatting/static checks, strict type checking, the Vitest suite, the
production build, all Core conformance vectors, `orgmd validate org`, `orgmd
doctor org`, and `npm pack` content verification. The existing
`.github/workflows/pages.yml` remains independent and continues publishing
`site/` on changes to `main`.

## Documentation, packaging, and deployment

`docs/cli.md` gives one-page command examples and explains diagnostics, exit
codes, clearance, advisory output, and safe adoption. README and site copy
will distinguish implemented Core behaviour from future enforcement. Security
guidance will document untrusted Markdown/YAML parsing, symlink and path
boundaries, atomic writes, denial-of-service limits, and the fact that advisory
projections are not enforcement. `CHANGELOG.md` receives a 0.5.0 section.

The package exports the supported library API, executable, JSON Schema, and
conformance metadata. `npm pack` is inspected and exercised in a clean
temporary consumer project. CI proves release readiness but receives no npm
token and does not publish. A maintainer performs `npm publish` explicitly
after review and version/tag approval. Merging to `main` deploys documentation
through the repository's established GitHub Pages workflow.

## Completion criteria

The design is complete when the implementation and conformance corpus pass
locally and in CI; the package installs and runs from its packed tarball; the
dogfood bundle passes validation and doctor after owner-ratified migration;
the documentation makes only implemented claims; the Pages workflow remains
intact; and no v0.6+ subsystem or release credential is introduced.

# ORG.md v0.5 Reference Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build and release-prepare the deterministic `orgmd` 0.5.0 Core reference implementation, five-command CLI, schema, conformance corpus, dogfood validation, and documentation.

**Architecture:** A private root npm workspace owns one publishable ESM package at `packages/orgmd`. Focused parser, validation, identifier, resolver, compiler, health, authoring, and CLI modules exchange typed immutable results and diagnostics; command handlers contain no domain rules. All projections flow from validated resolved contexts, and repository CI exercises the same public APIs and packed executable users receive.

**Tech Stack:** Node.js 20+, TypeScript 7.0.2, Vitest 4.1.11, YAML 2.9.0, Ajv 8.20.0, canonicalize 4.0.0, Prettier 3.9.6, npm workspaces, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-08-21-orgmd-v0.5-reference-implementation-design.md`

## Global Constraints

- Read `README.md`, `SPEC.md`, `NON-GOALS.md`, `GOVERNANCE.md`, `AGENT-BRIEF.md`, and the design spec before implementation; `SPEC.md` v0.3.1 wins over stale brief language.
- Do not modify `SPEC.md`, `NON-GOALS.md`, or `GOVERNANCE.md`; normative changes require an RFC.
- Support Node.js `>=20` and publish one ESM package named `orgmd` at version `0.5.0`.
- Revision status is exactly `draft | approved | rejected`; contestation and retirement exist only in `org.identity.lifecycle`.
- Implement Core disclosure Mode A only; do not implement MCP, gates, enforcement, signing, `org.lock`, adapters, retrieval, workflow, audit storage, Desk, hosted services, plugins, or benchmarks.
- Runtime dependencies are exactly `ajv@8.20.0`, `canonicalize@4.0.0`, and `yaml@2.9.0`; use `node:util` `parseArgs` rather than a CLI framework.
- All output is deterministic. Sort semantic collections by UTF-8 byte order, use RFC 8785 JCS, hash with SHA-256, inject dates in tests, and never depend on locale or filesystem enumeration order.
- Treat bundle input as untrusted. Reject invalid UTF-8/YAML, duplicate keys, traversal outside the requested bundle, unsafe symlinks, and writes that would overwrite unspecified files.
- Write tests before production behaviour, observe the expected failure, make the smallest passing change, rerun the focused test, then rerun the affected suite.
- Use DCO-signed commits (`git commit -s`) and preserve `.github/workflows/pages.yml` unchanged.
- Do not publish to npm, push, merge, or create a release automatically. Verify the tarball and leave external publication to an explicit maintainer action.
- The `org/` lifecycle migration is a proposed governance write. It must remain reviewable and attributed to `role.editor`; do not present tooling as the ratifying actor.

- [ ] **Step 3: Implement the byte decoder, fence-aware record scanner, and strict YAML mapping parser**

```ts
export interface ParseContentFileInput {
  readonly path: string;
  readonly domain: Domain;
  readonly bytes: Uint8Array;
  readonly limits?: Partial<ParserLimits>;
}

export interface ParserLimits {
  readonly maxFileBytes: number;
  readonly maxEntriesPerFile: number;
  readonly maxYamlAliases: number;
}

export function parseContentFile(input: ParseContentFileInput): OperationResult<readonly ParsedEntryRevision[]> {
  const text = decodeUtf8Fatal(input.bytes).replace(/^\uFEFF/, "").replace(/\r\n?/g, "\n");
  const records = scanEntryRecords(text);
  return materializeRevisions(records, input);
}
```

Configure YAML with YAML 1.2 and unique-key enforcement. Preserve unknown
front-matter keys in `extra`, but never treat them as semantic fields. Track
opening line numbers while scanning instead of recovering positions later.
Default limits are 16 MiB per file, 10,000 records per file, and 100 expanded
YAML aliases; a limit breach returns `parser.resource-limit` without partial
entries.

- [ ] **Step 4: Implement canonical entry, metadata, digest input, and content ID functions**

```ts
export function sha256Hex(bytes: string | Uint8Array): string {
  return createHash("sha256").update(bytes).digest("hex");
}

export function computeContentId(bundle: ValidatedBundle): string {
  const metadata = bundleMetadataCanonicalForm(bundle.metadata);
  const metadataHash = sha256Hex(canonicalize(metadata));
  const lines = ["!bundle-metadata", metadataHash];
  for (const revision of allRevisionHashEntries(bundle)) {
    lines.push(revision.id, sha256Hex(canonicalize(entryCanonicalForm(revision))));
  }
  return `sha256:${sha256Hex(`${lines.join("\n")}\n`)}`;
}
```

Hash every revision, including drafts and rejected revisions, because they are
bundle content. Sort first by bytewise `id`, then numeric `rev`; reject a
duplicate `(id, rev)`. This is the conservative reconciliation of §4.7's
revision sets with §7.1's ID sorting and duplicate-ID sentence. Do not silently
omit non-effective revisions from the content identifier.

Use the package `canonicalize`; throw no raw library errors. Convert failures
to `identifier.canonicalization-failed` diagnostics at the public boundary.

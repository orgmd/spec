ORG.md

One reviewed place for the words, rules, decisions and owners that help people and AI work consistently.

ORG.md is a portable contract for that organisational meaning. The 0.5.0 reference CLI validates human-readable bundles, resolves approved revisions along one organisational path, and compiles clearance-filtered advisory context for AGENTS.md and prompts.

Specification 0.3.1-draft · reference CLI 0.5.0 source-available and runnable from this repository · Pages live · npm package, Git tag and GitHub Release pending.

The current CLI emits advisory text only. It does not enforce actions, authenticate approvers, sync systems of record, or operate a hosted service.

Path

From working engine to usable workflow

The reference implementation proves the deterministic core. The next question is whether an organisation can operate it without asking every owner to become a Git expert.

  1. Working in v0.5

    Prove the engine

    Validate, diagnose and resolve local bundles, then generate two deterministic advisory views for review.

  2. Next POC

    Prove the workflow

    Let a non-technical owner propose a change through a tidy interface while Git records the reviewed source change.

  3. Later integration

    Connect the organisation

    Add identity-backed ratification, source adapters, signing, managed delivery, audit integration and interposed gates.

Direction, not a release promise. Only the first stage ships in v0.5. The Desk page is a local concept for exploring stage two.

§1

The problem

Every place you put AI (a coding agent, a customer bot, a staff assistant) needs to know what your organisation means: its words, rules, decisions and owners. Today each surface gets its own copy, pasted into a prompt here, paraphrased into a config there, half-remembered in a wiki. Here is one fact at one company, as five surfaces currently hold it:

eng repo · CLAUDE.md
consignment: another word for shipment
→ the software gets built on the wrong definition, mixing bookings and legs.
customer bot · system prompt
be helpful. estimate delivery times when customers ask.
→ promises ops can't keep; no policy exists on this surface at all.
warehouse agent · openclaw.yaml
# no definitions found
→ the agent improvises meaning, unsupervised, at 2am.
wiki · last edited 2024
we prioritise rail for long-haul freight.
→ a superseded decision, still being read as truth.
the product owner's head
correct, complete, current.
→ unavailable at scale, and a bottleneck by lunchtime.

Five copies, five meanings, no enforcement, no audit trail. Between people, this cost confusion. Agents make it worse: they build on stale meaning at machine speed, so a wrong definition now ships on every surface before lunch.

§2

The idea

How AI agents work inside a single codebase is standardised (AGENTS.md). How they connect to tools is standardised (MCP). What your organisation means — its vocabulary, decisions, policies and who owns them — has no widely adopted portable standard, so every AI tool re-invents it, and every re-invention drifts.

One codebase AGENTS.md — how agents work in a codebase ✓ standardised
Agents ↔ tools MCP · A2A — how agents reach tools & each other ✓ standardised
Your whole org ORG.md — what words, rules and decisions mean here ◯ open — this spec

The proposal is small: a handful of plain text files, versioned like code. Every entry names its owner and clearance label.

Canonical by exception

The specification supports entries sourced from existing systems of record. Source adapters are deployment integrations and are not included in v0.5.

Small on purpose

An entry earns its place only if an agent getting it wrong is expensive.

Borrow, never build

Deployments are intended to reuse existing identity, key-management and audit systems. Those integrations are outside the v0.5 CLI.

§3

How the pieces make one useful view

The organisation keeps many small statements. A consumer receives neither one giant file nor the whole company tree: it receives the resolved meaning that applies on one designated route.

Plain-language takeaway: ORG.md separates where meaning is owned from how each person or AI receives the part that applies to them.

How this scales beyond one team

A large organisation does not make org.md larger and larger. It distributes responsibility across small bundles. Each consumer resolves one root-to-consumer path. Sibling branches are not merged into that view.

vocabulary · glossary.md

Closest wins

companycase — any customer support ticketbroader meaning
claims teamcase — a claim under active assessmentwins for this team

Local language may replace a broader definition for its own subtree. The company meaning remains everywhere else.

policies · policies.md

Rules stack and tighten

companydata.export.* → escalatestill applies
claims teamdata.export.customer → denynarrower and stricter

Every policy on the path applies. A closer layer may tighten a same-ID rule, never weaken it.

decisions & owners

Authority stays anchored

companydec.009 — customer data stays in NZanchored here
team bundledec.009 — reworded local copydiscarded and flagged

A decision changes where it was made. Ownership may move only through explicit delegation.

Operating rule

Split by accountability, layer or storage boundary

Keep only meaning that is expensive to get wrong. Leave long rationale in its existing system and link to it. Put restricted raw material in separately protected storage; projection filtering is not access control.

Current v0.5 boundary

A bounded POC, not proven enterprise scale

The CLI has no organisation registry, remote or sibling composition, authenticated clearance, task-specific retrieval or enterprise-volume benchmark. It emits the full visible context on one local ancestor path.

§4

How it works

The current implementation uses familiar pieces: plain-text entries, deterministic validation and resolution, and generated advisory context. Delivery into a consumer remains a deployment choice.

A human records ratification in the bundle. The CLI selects the effective approved revision and generates text for review; it does not operate an approval system or deliver that text automatically.

01Write it once

An entry is a few lines of YAML and a sentence. Every one names its owner, its audience, and its status — so a machine can always answer who decided this, who may see it, is it current?

--- id: term.consignment owner: role.product-owner scope: public status: approved rev: 4 --- consignment — one customer booking. May span several shipments; never a synonym for one.

02Review it like code

The specification requires a human owner to ratify a revision. A Git pull request can record that review, but v0.5 does not verify the reviewer's identity or treat a merge itself as ratification.

pull request · glossary.md term.consignment rev 3 → 4 review recorded by the Git workflow status: approved is authored in the bundle

03Compile advisory context

The 0.5 CLI resolves a bundle and emits one of two advisory projections, filtered by clearance. What a projection omits is not a claim that a recipient cannot already access the raw bundle.

$ orgmd compile org --all --today 2026-08-21 → AGENTS.md fragments coding agents → system-prompt blocks bots · assistants both projections are advisory

04Review before delivery

Review generated text before placing it in a prompt or agent instruction file. Version 0.5 has no MCP server or policy gate, so it cannot interpose on actions or turn this context into runtime enforcement.

$ orgmd validate org validate: ok $ orgmd doctor org --today 2026-08-21 doctor: ok review generated context before use
§5

One source, controlled revisions

In §1, a wiki page last edited in 2024 was still telling every reader — human and machine — that the company prioritises rail. Here is the same update, made where meaning lives:

01

Edit. Ops moves the long-haul default from rail to coastal shipping. One entry changes — dec.014 — and, in a Git-based workflow, the change can be reviewed through a pull request.

dec.014 · rev 6 → 7
02

Ratify. The entry's owner — ops, not whoever edited the wiki last — approves. Rev 7 becomes the effective revision; rev 6 becomes history, not a lie left lying around.

status: approved
03

Future hardening. Signing and org.lock are future hardening; v0.5 has no signing or release seal.

future · no org.lock
04

Land advisory context. In v0.5, the CLI compiles only the coding agent's fragment and customer-bot prompt. Gate and handbook projections are future work.

2 advisory projections

And when people disagree — the normal case in a real organisation — disagreement is a state the format can hold, not a failure:

draft

Not selected by a conforming resolver or emitted as the effective organisational meaning. Its presence still changes bundle and context identifiers.

approved

Eligible to become the effective revision and appear in permitted projections.

rejected

Not selected as the effective revision.

Contestation and retirement are lifecycle states recorded only in org.identity.lifecycle; they do not extend the revision-status vocabulary.

§6

Your industry, your tools

Future projection examples — not shipped in v0.5. Gate and handbook destinations below illustrate later work; v0.5 ships only advisory agents-md and prompt projections.

The entry format stays the same. A large organisation may use many owned bundles, while the expensive-to-get-wrong meaning changes by industry. These are illustrative current and future destinations, not integrations shipped by v0.5:

Freight & logistics

Illustrative future integration · not included in v0.5

The rule: never let a bot promise a delivery time. Written once by ops, future integrations could carry it to the surfaces below.

the entry — a plain text file

--- id: policy.P-11 owner: own.ops scope: public status: approved action: customer.eta.promise effect: deny rev: 2 --- Never promise a delivery time. Quote the published service window; anything firmer is ops' call.

illustrative current and future destinations

customer bot · prompt blockv0.5 output format · placement is manual
"never promise a delivery time; quote the published service window."
→ the §1 failure, fixed at the source it drifted from.
warehouse agent · MCP gatefuture interposed gate
org.policy("customer.eta.promise") → deny
→ not a suggestion: where the agent's tool calls go through the gate, the call is refused before it runs, 2am included.
ops team · handbookfuture handbook profile
the same rule, one page, with its owner and revision.
→ people and agents read one truth, formatted for each.

Healthcare

Illustrative future integration · not included in v0.5

The rule: no patient record leaves the practice without the privacy officer sighting the request. The interesting part is who doesn't see the rule — and gets gated anyway.

the entry — a plain text file

--- id: policy.P-03 owner: own.privacy-officer scope: internal status: approved action: patient.record.disclose effect: escalate route: own.privacy-officer revisit: 2027-03-01 --- No patient record leaves the practice without the privacy officer sighting the request. Apply the organisation's Health Information Privacy Code 2020 policy.

illustrative current and future destinations

reception chatbot · public viewv0.5 clearance filtering · placement is manual
compiled out — scope: internal
→ the public bot never receives the wording, so it can't paraphrase or leak it. Its actions still hit the gate.
triage agent · MCP gatefuture interposed gate
org.policy("patient.record.disclose") → escalate · route: own.privacy-officer
→ a named human in the loop, resolved from ownership.md — not an email hardcoded into a prompt.
practice staff · prompt blockv0.5 output format · placement is manual
the full rule, with its owner and a revisit date.
→ past 2027-03-01 unconfirmed, the entry is flagged stale and the gate stops answering allow. Staleness is computed, never trusted.

Fintech

Illustrative future integration · not included in v0.5

The rule: agents may draft refunds, but above NZ$500 a human in finance issues them. One number, one home — and a paper trail for the regulator. To be exact about the split: the gate answers escalate to every payments.refund.issue, and the NZ$500 threshold lives in the rule's prose, applied by the finance person on the route — ORG.md carries meaning to the people and agents who act on it; it does not read amounts or classify raw business events.

the entry — a plain text file

--- id: policy.P-07 owner: own.finance scope: internal status: approved action: payments.refund.issue effect: escalate route: own.finance rev: 5 --- Agents may draft refunds at any amount; above NZ$500 a human in finance issues them.

illustrative current and future destinations

support agent · prompt contextv0.5 output format · placement is manual
"draft the refund; above NZ$500, hand it to finance."
→ the limit lives in one entry, not in nine prompts that each remember a different number.
back-office agent · MCP gatefuture interposed gate
org.policy("payments.refund.issue") → escalate · relied_upon: [policy.P-07]
→ the verdict names the rule it stood on, so "why did the agent stop?" has an answer.
your auditor · SIEMfuture audit integration
every verdict logged with the sealed bundle version that produced it.
→ "why did the agent do that?" becomes replayable, months later, against the exact meaning in force that day.

Airports & aviation

Illustrative future integration · not included in v0.5

The rule: nothing moves airside without an active clearance. Written once at the top of the airport's tree; Terminal 2 tightens it for its own apron. An operation this broad — airside, retail, security, ground handlers — is exactly why bundles nest.

the entry — a plain text file

--- id: policy.P-21 owner: own.airside-ops scope: internal status: approved action: airside.vehicle.dispatch effect: escalate route: own.duty-manager rev: 8 --- No vehicle dispatches airside without an active clearance. Terminals may narrow this for their own apron; none may weaken it.

illustrative current and future destinations

GSE dispatch agent · MCP gatefuture interposed gate
org.policy("airside.vehicle.dispatch") → escalate · route: own.duty-manager
→ routed to whoever holds the duty-manager role right now — a roster lookup, not a name that left last year.
terminal 2 · local bundlev0.5 layered resolution · local ancestors
adds a local rule: deny during low-visibility procedures.
→ a department can tighten the airport-wide rule for its own patch, never loosen it — one format, from a regional strip to a hub with forty departments.
contractor briefing · handbookfuture handbook profile
ground handlers and their agents read the same rule, current revision, before day one.
→ the workforce that churns hardest gets the meaning that drifts worst — solved at the source.

SaaS

Illustrative future integration · not included in v0.5

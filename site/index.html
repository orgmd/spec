ORG.md

One source of org meaning — written once, filtered, and delivered to every AI tool and every person.

§1

The problem

Every place you put AI (a coding agent, a customer bot, a staff assistant) needs to know what your organisation means: its words, rules, decisions and owners. Today each surface gets its own copy, pasted into a prompt here, paraphrased into a config there, half-remembered in a wiki. Here is one fact at one company, as five surfaces currently hold it:

eng repo · CLAUDE.md
consignment: another word for shipment
→ the software gets built on the wrong definition, mixing bookings and legs.
customer bot · system prompt
be helpful. estimate delivery times when customers ask.
→ promises ops can't keep; no policy exists on this surface at all.
warehouse agent · openclaw.yaml
# no definitions found
→ the agent improvises meaning, unsupervised, at 2am.
wiki · last edited 2024
we prioritise rail for long-haul freight.
→ a superseded decision, still being read as truth.
the product owner's head
correct, complete, current.
→ unavailable at scale, and a bottleneck by lunchtime.

Five copies, five meanings, no enforcement, no audit trail. Between people, this cost confusion. Agents make it worse: they build on stale meaning at machine speed, so a wrong definition now ships on every surface before lunch.

§2

The idea

How AI agents work inside a single codebase is standardised (AGENTS.md). How they connect to tools is standardised (MCP). What your organisation means — its vocabulary, decisions, policies and who owns them — has no widely adopted portable standard, so every AI tool re-invents it, and every re-invention drifts.

One codebase AGENTS.md — how agents work in a codebase ✓ standardised
Agents ↔ tools MCP · A2A — how agents reach tools & each other ✓ standardised
Your whole org ORG.md — what words, rules and decisions mean here ◯ open — this spec

The proposal is small: a handful of plain text files, versioned like code, sitting above your repositories. Every entry names its owner and who may see it.

org/ ├── org.md # identity, mission, tone ├── glossary.md # shared vocabulary · who sees each entry ├── decisions/ # active decisions, with owners ├── policies.md # what agents may / must-not do ├── ownership.md # who decides what · where to escalate ├── done.md # definitions of done └── org.lock # release seal · tamper-evident
Canonical by exception

Entries sync in from your existing systems of record, so this doesn't become another wiki that quietly rots.

Small on purpose

An entry earns its place only if an agent getting it wrong is expensive.

Borrow, never build

Sign-in, keys and audit come from the systems your company already runs. ORG.md owns a format and a compiler, nothing else.

§3

How it works

Nothing in the pipeline is new. Meaning is written as plain text, reviewed like code, compiled per audience, and delivered in whatever form each consumer already reads. The only novel part is agreeing on the format.

In plain terms: someone writes a rule down once, the right person signs it off, and software carries the right version of it to every bot, agent and colleague. The grey boxes below are the real thing — ordinary text files a person can read without any tooling.

01Write it once

An entry is a few lines of YAML and a sentence. Every one names its owner, its audience, and its status — so a machine can always answer who decided this, who may see it, is it current?

--- id: term.consignment owner: role.product-owner scope: public status: approved rev: 4 --- consignment — one customer booking. May span several shipments; never a synonym for one.

02Review it like code

Changes arrive as pull requests. Only the entry's named owner can ratify one — the merge is the approval, and the git history is the audit trail. No steering committee, no wiki edit wars.

pull request · glossary.md term.consignment rev 3 → 4 ✓ approved · role.product-owner merged · sealed into org.lock

03Compile by audience

One command emits a projection per audience, filtered by who may see what. What an audience may not see isn't redacted or watermarked — it's absent, so it can't be paraphrased or leaked.

$ orgmd compile --all → AGENTS.md fragments coding agents → system-prompt blocks bots · assistants → MCP gate tables autonomous agents → handbook pages people, per role

04Deliver — and enforce

Tools that read prose get the text. Agents that act get a gate: before doing something, the agent asks "may I?" and receives allow, escalate or deny — the same answer every time, naming the rule it stood on and the person to ask.

org.policy("payments.refund.issue") → verdict: escalate relied_upon: [policy.P-07] route: own.finance "pause — this one goes to finance, under rule P-07."
§4

One change, everywhere

In §1, a wiki page last edited in 2024 was still telling every reader — human and machine — that the company prioritises rail. Here is the same update, made where meaning lives:

01

Edit. Ops moves the long-haul default from rail to coastal shipping. One entry changes — dec.014 — and the change opens as a pull request.

dec.014 · rev 6 → 7
02

Ratify. The entry's owner — ops, not whoever edited the wiki last — approves. Rev 7 becomes the effective revision; rev 6 becomes history, not a lie left lying around.

status: approved
03

Seal. The bundle's release seal is re-signed, so every consumer can verify it holds the current, untampered version — and prove which version produced any answer.

org.lock ✓
04

Land. Every projection recompiles: the coding agent's fragment, the customer bot's prompt, the gate, the handbook. Nobody chases surfaces; none is missed.

4 audiences · 0 chased

And when people disagree — the normal case in a real organisation — disagreement is a state the format can hold, not a failure:

draft

Proposed meaning. Never delivered to any consumer, so a half-formed idea can't ship.

approved

Ratified by the owner. This is what every surface receives.

contested

Under dispute. Marked visibly everywhere it appears; agents that would rely on it must stop and escalate to the owner instead of guessing.

superseded

Retired but kept. History stays auditable without being mistaken for truth.

§5

Your industry, your tools

The bundle is the same handful of files everywhere. What changes is which entry is expensive to get wrong — and which tools are listening. One entry per industry, and the three surfaces it lands on:

Freight & logistics

The rule: never let a bot promise a delivery time. Written once by ops, it reaches every surface below — including the ones from §1 that used to drift.

the entry — a plain text file

--- id: policy.P-11 owner: own.ops scope: public status: approved action: customer.eta.promise effect: deny rev: 2 --- Never promise a delivery time. Quote the published service window; anything firmer is ops' call.

where it lands

customer bot · intercom prompt
"never promise a delivery time; quote the published service window."
→ the §1 failure, fixed at the source it drifted from.
warehouse agent · mcp gate
org.policy("customer.eta.promise") → deny
→ not a suggestion: where the agent's tool calls go through the gate, the call is refused before it runs, 2am included.
ops team · handbook
the same rule, one page, with its owner and revision.
→ people and agents read one truth, formatted for each.

Healthcare

The rule: no patient record leaves the practice without the privacy officer sighting the request. The interesting part is who doesn't see the rule — and gets gated anyway.

the entry — a plain text file

--- id: policy.P-03 owner: own.privacy-officer scope: internal status: approved action: patient.record.disclose effect: escalate route: own.privacy-officer revisit: 2027-03-01 --- No patient record leaves the practice without the privacy officer sighting the request. HIPC 2020 applies.

where it lands

reception chatbot · public scope
compiled out — scope: internal
→ the public bot never receives the wording, so it can't paraphrase or leak it. Its actions still hit the gate.
triage agent · mcp gate
org.policy("patient.record.disclose") → escalate · route: own.privacy-officer
→ a named human in the loop, resolved from ownership.md — not an email hardcoded into a prompt.
practice staff · copilot block
the full rule, with its owner and a revisit date.
→ past 2027-03-01 unconfirmed, the entry is flagged stale and the gate stops answering allow. Staleness is computed, never trusted.

Fintech

The rule: agents may draft refunds, but above NZ$500 a human in finance issues them. One number, one home — and a paper trail for the regulator. To be exact about the split: the gate answers escalate to every payments.refund.issue, and the NZ$500 threshold lives in the rule's prose, applied by the finance person on the route — ORG.md carries meaning to the people and agents who act on it; it does not read amounts or classify raw business events.

the entry — a plain text file

--- id: policy.P-07 owner: own.finance scope: internal status: approved action: payments.refund.issue effect: escalate route: own.finance rev: 5 --- Agents may draft refunds at any amount; above NZ$500 a human in finance issues them.

where it lands

support agent · zendesk / fin
"draft the refund; above NZ$500, hand it to finance."
→ the limit lives in one entry, not in nine prompts that each remember a different number.
back-office agent · mcp gate
org.policy("payments.refund.issue") → escalate · relied_upon: [policy.P-07]
→ the verdict names the rule it stood on, so "why did the agent stop?" has an answer.
your auditor · siem
every verdict logged with the sealed bundle version that produced it.
→ "why did the agent do that?" becomes replayable, months later, against the exact meaning in force that day.

Airports & aviation

The rule: nothing moves airside without an active clearance. Written once at the top of the airport's tree; Terminal 2 tightens it for its own apron. An operation this broad — airside, retail, security, ground handlers — is exactly why bundles nest.

the entry — a plain text file

--- id: policy.P-21 owner: own.airside-ops scope: internal status: approved action: airside.vehicle.dispatch effect: escalate route: own.duty-manager rev: 8 --- No vehicle dispatches airside without an active clearance. Terminals may narrow this for their own apron; none may weaken it.

where it lands

gse dispatch agent · mcp gate
org.policy("airside.vehicle.dispatch") → escalate · route: own.duty-manager
→ routed to whoever holds the duty-manager role right now — a roster lookup, not a name that left last year.
terminal 2 · its own bundle
adds a local rule: deny during low-visibility procedures.
→ a department can tighten the airport-wide rule for its own patch, never loosen it — one format, from a regional strip to a hub with forty departments.
contractor briefing · handbook
ground handlers and their agents read the same rule, current revision, before day one.
→ the workforce that churns hardest gets the meaning that drifts worst — solved at the source.

SaaS

The rule: "done" means shipped behind a flag with telemetry and a rollback path. Not a policy — a shared definition, which is most of what teams actually argue about.

the entry — a plain text file

--- id: done.feature owner: role.eng-lead scope: internal status: approved rev: 3 --- A feature is done when it ships behind a flag, with telemetry and a rollback path — not when the pull request merges.

where it lands

coding agent · claude code / cursor
the definition of done, in the context window, on every task.
→ agents stop declaring victory at "the tests pass".
review bot · ci
cites done.feature when a PR claims done without a flag.
→ review comments point at a shared source instead of a reviewer's taste.
new engineer · handbook
the same words, on day one.
→ onboarding stops being oral tradition.

A two-person outfit runs all of this as one bundle. A larger organisation — board, exec, business units, teams — gives each layer its own, and a consumer's tools resolve down one path of that tree. The part that makes layers safe: three kinds of meaning travel by three different rules.

vocabulary · glossary.md

Closest wins

org case — any customer support ticket overridden below
claims team case — a claim under active assessment wins, for this team

Local language is allowed to be local. The org's meaning still holds everywhere else.

policies · policies.md

Stack — tighten only

org data.export.* → escalate still applies
claims team data.export.customer → deny narrows — allowed

Rules stack down the tree, and a closer layer may only make them stricter. The resolver rejects anything weaker — structurally, not on trust.

decisions & owners · decisions/

The anchor wins

board dec.009 — customer data stays in NZ anchored — wins
a team bundle dec.009 — reworded local copy discarded · flagged

Authority resolves from the top. Ownership can be delegated explicitly; decisions never — a board decision changes only where it was made.

Every layer can add meaning and tighten rules for its own subtree; none can take or weaken what sits above. Start as one bundle; split a layer out only when it needs to own its own meaning.

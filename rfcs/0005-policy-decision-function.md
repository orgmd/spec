# RFC 0005 — Policy entries as a decision function: `action`, `effect`, `route`

- **Status:** accepted
- **Author:** Matt (BoundFor Ltd)
- **Opened:** 2026-08-21
- **Comment period ends:** 2026-09-04
- **Resolves:** orgmd/spec#5

## Motivation

SPEC §6.3 requires `org.policy(action)` responses to be deterministic for a
given (bundle versions, identity, action). SPEC §4.4 requires a policy entry
to be "expressible as a decision function over an action". Neither is
achievable today: the §4 entry model has no `action`, no `effect`, and no
`route` field, and the spec defines no rule for deciding which entries match
an action or how their answers combine. A policy is a paragraph of prose.

Two conforming resolvers can therefore return different verdicts for the same
action without either being wrong, which contradicts §5's resolver-conformance
guarantee and §11's behavioural conformance claim.

The gap is not theoretical. This project's own bundle already invents a
convention in prose — `org/policies.md` writes ``action: `edit_spec_normative`
→ escalate: RFC process`` — because the format it documents cannot express
what the file needs to say. When the reference bundle has to work around the
entry model, the entry model is wrong.

`org.define(term)` has the same defect at lower severity: the spec does not
say how the caller's argument is matched against entry `id`s or labels, nor
what a miss returns. Implementations will diverge, and a gate that answers a
miss with prose invites a consumer to treat an invented definition as
canonical.

## Design

### 1. New front-matter fields for constraint entries

Every entry in a **constraint** domain (SPEC §3; today, `policies.md`) MUST
carry, in addition to the §4 fields:

| Field    | Requirement | Meaning |
|----------|-------------|---------|
| `action` | MUST | One action token or one action pattern (§2 below) |
| `effect` | MUST | `allow` \| `escalate` \| `deny` |
| `route`  | MUST when `effect: escalate` | The owner or escalation target the consumer is sent to |

An entry in a **definition** domain MUST NOT carry `action`, `effect`, or
`route`. Validators MUST reject a constraint entry missing `action` or
`effect`, a constraint entry with `effect: escalate` and no `route`, and any
entry whose `effect` is not one of the three listed tokens.

`route` MUST be an identifier resolvable in the tree's ownership domain (an
`own.*` or role identifier). Free text MUST NOT be accepted; the escalation
target is machine-actionable or it is not an escalation.

An entry MAY carry more than one constraint by being written as more than one
entry. A single entry MUST NOT carry a list of actions or effects: one entry,
one action, one effect. This keeps `id` a stable handle on exactly one rule,
which the narrowing rule (RFC 0006), the reliance rule (RFC 0010) and audit
(§8) all depend on.

The entry body remains prose. The body explains the rule to a human; the
fields decide it. Where body and fields disagree, the fields govern, and
tooling SHOULD flag the divergence for the owner.

### 2. Action grammar

Action tokens are dot-separated segments, deliberately close to the shape of
tool names an implementation is already routing.

```
action-token   = segment *( "." segment )
action-pattern = segment *( "." segment ) "." "*"
segment        = lower *( lower / digit / "_" / "-" )
lower          = %x61-7A          ; a-z
digit          = %x30-39          ; 0-9
```

Normative constraints on the grammar:

- An action value MUST match `action-token` or `action-pattern`.
- `*` MUST appear only as the whole final segment, and MUST NOT be the only
  segment. `billing.*` is valid; `*`, `bill*.read`, `a.*.b` are not.
- Tokens MUST be US-ASCII lowercase as generated by the grammar. Validators
  MUST reject any other input rather than case-folding or transliterating it;
  silent normalisation is a divergence source between implementations.
- Comparison of segments is byte equality after Unicode NFC normalisation of
  the *input action* supplied to `org.policy`. An input action that does not
  match `action-token` after NFC normalisation MUST be rejected by the gate
  with a malformed-input error; it MUST NOT be treated as an uncovered action,
  because "reject" and "escalate" are different answers.

The single-trailing-wildcard restriction is intentional. Patterns with
interior or multiple wildcards make containment and specificity comparisons
non-trivial and, in every prior policy language, the source of surprising
overlaps. With this grammar, specificity is a segment count and containment is
a prefix test — both auditable by eye, which SPEC's own bar for the resolver
requires.

### 3. Matching

Given an input action `A`, an entry with action value `P` **matches** `A`
when:

- `P` is an action token and `P` equals `A`; or
- `P` is an action pattern with literal prefix segments `p1..pn` and `A` has
  at least `n+1` segments whose first `n` segments equal `p1..pn`.

A pattern MUST NOT match an action equal to its own literal prefix:
`billing.*` does not match `billing`. Where both are wanted, author both
entries.

The **specificity** of a matching entry is the number of literal segments in
its action value. An exact token is more specific than any pattern with the
same segment count; formally, specificity is ordered first by literal segment
count, then by exact-before-pattern.

### 4. Verdict computation

The verdict is computed in two stages. Stage 1 decides what one bundle says;
stage 2 combines bundles. Splitting them is what makes exceptions expressible
without letting a closer bundle widen a rule it inherited.

**Effect strength** is the total order `deny > escalate > allow`.

**Stage 1 — local verdict, per bundle.** For each bundle on the node path,
the resolver MUST:

1. Take the set of that bundle's constraint entries that match `A` and are
   eligible under RFC 0008 (`status` handling per §4.1; clearance MUST NOT
   affect membership).
2. If the set is empty, the bundle has no local verdict and MUST be skipped in
   stage 2.
3. Otherwise, retain only the entries of greatest specificity.
4. The bundle's local verdict is the strongest `effect` among the retained
   entries, and the local relied-upon set is the `id`s of the retained entries
   carrying that effect.

**Stage 2 — effective verdict, across bundles.** The effective verdict is the
**strongest** local verdict of any bundle on the path. The relied-upon set is
the union of the local relied-upon sets of every bundle whose local verdict
equals the effective verdict.

Stage 2 MUST NOT compare specificity across bundles. A closer bundle can
therefore make a rule stricter and can never make it weaker, which is
constitution principle 5 realised as arithmetic rather than as prose. Stage 2
is commutative and associative over bundles, so the verdict does not depend on
path traversal order.

**Uncovered actions.** Where no bundle produces a local verdict, the gate MUST
return `escalate`, per §6.3 and constitution principle 8. The response MUST
distinguish this case from an authored `escalate` (see §5 below), because the
two require different follow-up: an uncovered action indicates missing meaning
and SHOULD be counted by drift tooling (§10).

**Route.** Where the effective verdict is `escalate` and the relied-upon set
is non-empty, the response MUST carry the `route` of every relied-upon entry.
Where the relied-upon set is empty (uncovered action), the response MUST carry
the escalation target of the node itself, taken from the ownership domain.

**Determinism.** Matching, specificity, stage 1 and stage 2 are total
functions of (bundle versions, identity, action). Two conforming resolvers
given the same inputs MUST produce the same verdict, the same relied-upon set
and the same routes. Ties are impossible by construction: within a bundle,
retained entries of equal specificity are collapsed by effect strength, and
two entries with the same `id` in one bundle are already a validation error.

### 5. Gate response shape

`org.policy(action)` responses MUST carry at least:

- `verdict` — `allow` | `escalate` | `deny`
- `reason` — `matched` | `uncovered` | `resolution_error` (RFC 0007)
- `relied_upon` — the relied-upon set, subject to the withholding rules of
  RFC 0008
- `routes` — required when `verdict` is `escalate`
- `bundle_versions` — per §6.3

Gates MUST NOT return free prose in place of a verdict, and MUST NOT return a
verdict absent from the four-token `verdict` vocabulary.

### 6. `org.define(term)` lookup

The argument to `org.define` is a **lookup key**. Resolvers MUST apply, in
order:

1. **Id lookup.** If the key matches an entry `id` in the effective context
   byte for byte, that entry is the result.
2. **Label lookup.** Otherwise the key is normalised: Unicode NFC; lowercase;
   trim leading and trailing whitespace and punctuation; replace each internal
   run of whitespace or `_` with a single `-`; drop any remaining character
   outside `a-z0-9-`. The normalised key `k` is then compared against
   `term.<k>` and against the identically-normalised form of each definition
   entry's display label.
3. If neither step yields exactly one entry, the lookup is a **miss**.

Resolvers MUST NOT perform fuzzy, stemmed, embedding-based or otherwise
approximate matching. ORG.md answers "what is canonical", not "what is
relevant" (NON-GOALS #2); an approximate definition lookup is a retrieval
system with a gate's authority.

A miss MUST be returned as a structured response carrying `found: false` and a
`reason`:

- `not_defined` — no entry matched.
- `ambiguous` — more than one entry matched. The response MUST carry the
  candidate `id`s that are within the consumer's clearance, and MUST report
  the withheld remainder per RFC 0008. An ambiguous lookup is an authoring
  defect and SHOULD be surfaced by drift tooling (§10).
- `withheld` / `resolution_error` — per RFC 0008 and RFC 0007.

Gates MUST NOT synthesise, paraphrase or infer a definition on a miss.
Consumers MUST treat a miss as absence of canonical meaning, not as licence to
supply their own.

## Alternatives considered

**Do nothing.** Leave policies as prose and the gate's determinism claim
unbacked. Rejected: §6.3, §5's resolver guarantee and §11's behavioural
conformance are all unsatisfiable without this, and the project's own bundle
has already invented a substitute convention in prose. Doing nothing means
shipping a determinism claim the specification cannot cash.

**Full policy language (Rego, Cedar, or an ORG.md-native expression syntax).**
Rejected for the canonical layer. It moves authorship out of reach of the
people accountable for the meaning, and it makes the bundle a program rather
than a record. DEC-0006 points the other way round: OPA and Cedar are
*compile targets*. The three fields in this RFC compile to a Cedar `permit` /
`forbid` pair or a Rego rule mechanically; a Rego source of truth compiles to
nothing.

**Condition or attribute predicates on entries (`when:`, resource matching,
time windows).** Rejected for now. Every predicate added is a term in the
determinism proof and a new bench surface. If a real deployment demonstrates
that an action-shaped rule cannot express a needed constraint, that is a
separate RFC with the evidence attached.

**Match precedence by specificity across the whole path** (the form proposed
on the issue: exact > pattern globally, effect precedence at ties). Rejected
in favour of the two-stage rule. Global specificity lets a repo-level
`billing.refund: allow` override a division-level `billing.*: deny`, which is
exactly the widening §5 and constitution principle 5 forbid. The two-stage
rule keeps the useful part — local exceptions — and makes the widening
unrepresentable rather than merely prohibited.

**Ordered rule lists (first match wins, as in firewall ACLs).** Rejected:
order across bundles is not well-defined once entries come from several nodes,
and order-dependence is precisely the property that makes ACLs hard to audit.

**Free-text `route`.** Rejected: an escalation target a machine cannot resolve
is a comment.

## Conformance impact

**Core.** The three fields and the action grammar are Core: they are
front-matter and a regular expression, and a validator for them is an
afternoon's work, consistent with §11's Core bar. Constraint entries without
`action`/`effect` become invalid at Core.

**Extended.** The matching, specificity and two-stage verdict rules bind any
component that computes a verdict — in practice the §6.3 gate, which is
Extended. Core implementations emit constraint entries into advisory
projections and are not required to compute verdicts; a Core implementation
MUST NOT claim deterministic policy answers. The §6.3 determinism sentence
should be read as scoped to Extended and above, and RFC 0009 further scopes
what "enforced" may be claimed for.

**Migration.** `org/policies.md` in this repository must be rewritten to carry
the fields it currently encodes in prose. `schema/entry.schema.json`
(AGENT-BRIEF step 1) gains the three fields and the grammar pattern.

**Bench tests to add** (resolver track unless noted):

- `policy/exact-match` — exact token matches, verdict returned.
- `policy/pattern-match` — `billing.*` matches `billing.refund`, does not
  match `billing`.
- `policy/specificity-local` — within one bundle, exact `allow` beats pattern
  `deny`.
- `policy/no-cross-bundle-override` — repo `billing.refund: allow` under
  division `billing.*: deny` yields `deny`.
- `policy/effect-precedence-tie` — same bundle, same specificity, `deny` and
  `allow` present, yields `deny`.
- `policy/uncovered-escalates` — uncovered action returns `escalate` with
  `reason: uncovered` and a node escalation target.
- `policy/malformed-action-rejected` — uppercase, empty, interior-wildcard and
  bare-`*` inputs are rejected, not escalated.
- `policy/order-independence` — permuting bundle traversal order yields
  byte-identical output.
- `define/id-lookup`, `define/label-normalisation`,
  `define/ambiguous-miss`, `define/no-synthesis` (agent track: consumer
  receiving a miss must not proceed on an invented definition).

## Constitution check

No amendment required.

- **Principle 5** (closer scopes may narrow, never widen) is strengthened:
  stage 2 makes widening arithmetically unrepresentable rather than prohibited
  in prose.
- **Principle 8** (unknown authority escalates) is preserved and made
  explicit: uncovered actions escalate and are distinguishable from authored
  escalations, so missing meaning is measurable (§10).
- **Principle 10** (behavioural conformance) is served: the rules above are
  what the bench can test.
- **Principle 11** (vendor neutrality) is preserved: the grammar names no
  vendor and compiles to several targets.
- **DEC-0007 / NON-GOALS #9** (no typed relationships) is not touched. `action`
  and `effect` are scalar attributes of a single entry. They express no
  relation between entries, and nothing in the matching or verdict rules
  requires an entry to reference another entry.
- **DEC-0006** (profile, don't invent) is honoured: the field triple is the
  smallest structure that compiles to OPA and Cedar without a translation
  layer that has to guess.
